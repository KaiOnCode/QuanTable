# Broker Plus Frozen Contract And Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the current broker implementation into a broker-owned execution-domain contract that can be consumed by future FastAPI, React, audit, HITL, and strategy-account flows without implementing those outer systems here.

**Architecture:** Keep the broker core responsible for execution, account isolation, risk, fills, ledger records, and broker-domain events. Add a broker-owned view/serializer layer in `broker/views.py` for API/front-end contracts, while keeping FastAPI, ContextStore, notification channels, and full HITL workflow out of scope. Use protocols for persistence boundaries and in-memory implementations for first-stage validation.

**Tech Stack:** Python, Pydantic, pandas, pytest, `uv`, `ruff`, `basedpyright`, existing `broker/`, `agentgraph/`, `streamlit_app.py` test harnesses.

## 2. Frozen Decisions

1. Broker owns the stable API/front-end contract for execution-domain data.
2. First-stage DTOs and serializers live in a single file: `broker/views.py`.
3. `strategy_id`, `account_id`, `session_id`, and `decision_id` enter broker core models as optional transition fields.
4. `decision_id` is generated by PM/orchestrator and only received, propagated, and persisted by broker.
5. `MockBrokerEngine` first-stage design supports real account isolation by `account_id`, not just metadata tagging.
6. First-stage strategy/account relation is one strategy to one account.
7. `session_id` means one Agent graph run / one execution turn.
8. Percentages use internal decimal fractions for broker config/risk/portfolio math and API/View percentage points for external output.
9. API/View enums are lower-case and front-end-facing.
10. `OrderStatus.NEW` maps to `pending`.
11. HITL `pending` returns a structured `ExecutionReportView` pending variant.
12. `ExecutionReportView.status` values are `pending`, `skipped`, `held`, `executed`, `rejected`, and `failed`.
13. HITL trigger rules belong to future `hitl/` manager or graph nodes, not broker.
14. Broker does not import FastAPI or ContextStore. Broker depends on protocols only.
15. First-stage event persistence covers broker execution-domain events only.
16. Failed orders and risk rejections do not enter the trade ledger. They enter event sink and order views.
17. Broker events need monotonic `sequence` per `(strategy_id, account_id)`, assigned by event sink/backend.
18. Backtest JSON contract first-stage scope is execution backtest only.
19. Multi-ticker execution backtest uses one shared strategy account.
20. Benchmark defaults to `SPY`, but request/result must carry `benchmark_symbol`.
21. `BacktestResultView` is a synchronous completed result. Future API wraps it with `backtest_id` and job status outside broker.
22. Formal approval domain belongs to future `hitl/`. Broker only records an approval snapshot inside `ExecutionReportView`.
23. `approval_status="modified"` directly executes the modified target and records original and modified targets.
24. `execution_enabled=False` returns `ExecutionReportView(status="skipped")` and does not write broker event sink.
25. PM `HOLD` and target-already-satisfied return `ExecutionReportView(status="held")` and do not write broker event sink.
26. Missing market price / execution precondition failure returns `ExecutionReportView(status="failed")` and writes `execution_failed`.
27. Risk rejection returns `ExecutionReportView(status="rejected")`, includes the rejected order, has no fills, and writes `risk_check_failed` plus `order_rejected`.
28. `OrderView.commission` is the sum of fees from all fills for that order; zero for unfilled/rejected orders.
29. `OrderView.filled_quantity` and `filled_avg_price` are fill aggregates; no fills means `0` and `None`.
30. `PositionView` uses best available mark price plus `price_source`: `market`, `last_close`, or `avg_cost_fallback`.
31. `TradeView` comes from `TradeLedger` / `LedgerFillRecord`, not naked `Fill`.
32. SQLite and ContextStore adapters are out of first-stage scope; define protocol boundaries and in-memory implementations only.

## 3. Approaches Considered

### Recommended: Broker-Owned Contract With Protocol Persistence

Broker owns `broker/views.py`, identity fields, account isolation, execution reports, and broker-domain event protocols. API/server layers later become thin adapters.

Trade-off: broker package becomes more explicit about external contract shape. This is acceptable because the contract is still execution-domain data, not HTTP behavior.

### Alternative: Server-Owned DTO Contract

Keep broker purely internal and define DTOs in future `server/schemas/broker.py`.

Trade-off: this keeps broker smaller, but leaves the currently urgent merge contract undefined until the server layer exists. It also makes it easier for future API code to duplicate broker semantics incorrectly.

### Alternative: Full Platform Slice Now

Implement broker views, FastAPI routes, SQLite/ContextStore adapters, and HITL service together.

Trade-off: this is closer to the final product but crosses current ownership boundaries. It would mix broker, API, storage, and HITL workflow into one risky batch.

## 4. Design Contract

### 4.1 File Responsibilities

- `broker/models.py`: core execution-domain models only. Add identity and approval snapshot fields where they describe broker execution results, not HITL workflow policy.
- `broker/engine.py`: mock execution engine, account-isolated by `account_id`, still using in-memory state.
- `broker/events.py`: broker event model and event sink protocol/in-memory sink.
- `broker/ledger.py`: trade/snapshot ledger records and backend protocol. Ledger remains source of truth for trades and performance inputs.
- `broker/views.py`: external API/front-end-facing Pydantic views and serializer functions. No matching, risk, persistence, or HTTP code.
- `broker/gateway.py`: protocol for broker operations. Add account-aware signatures only where needed to expose isolated account state.
- `broker/backtest_runner.py`: execution backtest runner; can still return Python objects internally, but must be serializable through `BacktestResultView`.
- `agentgraph/execution_node.py`: converts AgentState/PM decision into broker order or structured non-order execution report.
- `agentgraph/orchestrator.py`: keeps graph wiring; exposes execution hook injection cleanly.
- `streamlit_app.py`: can continue consuming current DataFrames until serializer-backed dashboard migration is explicitly planned.

### 4.2 Identity Semantics

- `strategy_id`: long-lived strategy/config/performance owner.
- `account_id`: isolated trading account; first-stage default is derived one-to-one from `strategy_id` or `"default"`.
- `session_id`: one Agent graph run / one execution turn.
- `decision_id`: one PM decision; generated upstream by PM/orchestrator, propagated through order, fill, report, ledger, and events.

`session_id` must not be used as strategy, account, or decision identity.

### 4.3 Percent And Enum Semantics

- Internal broker math uses decimal fractions: `0.1` means 10%.
- API/View output uses percentage points: `10.0` means 10%.
- AgentState inputs `Target_position_pct` and `current_position_pct` remain percentage points.
- View enums are lower-case:
  - side: `buy`, `sell`
  - order type: `market`, `limit`
  - order status: `pending`, `executed`, `cancelled`, `rejected`
  - position side: `long`, `short`, `flat`
- Internal enums remain unchanged unless a task explicitly says otherwise.

### 4.4 Execution Report Semantics

`ExecutionReportView.status` values:

- `pending`: waiting for approval; no order placed.
- `skipped`: execution disabled by caller; no broker event.
- `held`: PM held or target already satisfied; no broker event.
- `executed`: order submitted and filled under the current engine behavior.
- `rejected`: approval rejected/timed out or broker risk rejected.
- `failed`: system/data precondition failure such as missing market price.

Approval data is a nested snapshot in the report, not a broker-owned HITL model:

```text
approval_id
approval_status
approval_reason
reviewer
reviewer_notes
original_target_pct
modified_target_pct
```

Future `hitl/` owns approval request/result models, policy rules, notification, and rerun workflow.

### 4.5 Event And Ledger Semantics

- Ledger stores fills/trades and daily snapshots only.
- Rejected orders and risk failures do not create trade records.
- Broker event sink stores execution-domain events:
  - `order_placed`
  - `order_filled`
  - `order_canceled`
  - `risk_check_failed`
  - `order_rejected`
  - `execution_pending`
  - `execution_rejected`
  - `execution_failed`
- `execution_enabled=False`, PM `HOLD`, and target already satisfied return reports but do not write broker event sink.
- Event sink assigns monotonic `sequence` per `(strategy_id, account_id)`.

### 4.6 View Contract

First-stage `broker/views.py` should expose these view models and serializers:

- `AccountView`
- `PositionView`
- `OrderView`
- `FillView`
- `TradeView`
- `ApprovalSnapshotView`
- `ExecutionReportView`
- `BrokerEventView`
- `PerformanceMetricsView`
- `BacktestConfigView`
- `BacktestSeriesPointView`
- `BacktestResultView`

`PositionView.current_price` uses best available mark:

1. current market mark from broker
2. last close / last known mark if available
3. `avg_cost` fallback

The chosen source must be visible through `price_source`.

`TradeView` is built from ledger records. Naked fills are execution details, not the public trade log source of truth.

### 4.7 Backtest JSON Contract

First-stage `BacktestResultView` is synchronous and completed:

```text
status = "completed"
config
summary
series
trades
```

Future API job wrappers own `backtest_id`, submitted/completed timestamps, and asynchronous status.

Execution backtest supports multiple tickers in one shared strategy account. Benchmark defaults to `SPY`, and `benchmark_symbol` must be present in config/result.

## 6. Implementation Order

1. Phase 0: documentation alignment, including the `02` checklist rewrite and this section's schedule fold-in.
2. Phase 1 / Task 1: identity fields.
3. Phase 1 / Task 3: event sink protocol.
4. Phase 2 / Task 2: account-isolated engine.
5. Phase 3 / Task 4: view/serializer layer.
6. Phase 4 / Task 5: structured execution reports and HITL safety semantics.
7. Phase 5 / Task 6: backtest JSON contract.

10. Phase 8: integration branch work for FastAPI, React, ContextStore/MCP/notifications, README merge, and end-to-end smoke.

This order fixes identity and event boundaries before account isolation, then stabilizes the external view contract before changing the execution-node return shape. Platform integration work must wait until the broker-owned contract passes the Phase 7 gate and then proceed on the integration branch.
